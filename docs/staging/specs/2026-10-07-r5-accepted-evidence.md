# R5 baseline and accepted-evidence primitives

status: implementation spec for #80; this does not revise the settled architecture.
authority: issue #80; `docs/staging/specs/2026-10-01-governance-execution-separation.md` at `6b4e83dc38efdd83117841cee012aa8873addafc`; normative executor contract at the same revision.
convention: Python 3.9; provider code remains in `scripts/agent_workflow.py`; regression tests use `unittest` and deterministic temporary Git repositories; workflow failures use `WorkflowError`; persistent state updates retain the existing locks, atomic replacement, and compare-and-swap revision checks.

## Contract

- R5 operates only on the operation-bound, Fidenaut-created Git worktree on the same host. Worktree creation, arbitrary external worktrees, cross-host execution, submodules, non-Git inputs, executor/provider behavior, and publication transactions remain out of scope.
- Admission captures the worktree identity, `HEAD`, and exact status/worktree baseline before reserving the operation. Acceptance revalidates the same worktree and `HEAD`, computes the final snapshot and delta, validates scope and evidence, and only then permits a governance-verified terminal transition.
- The operation's immutable Fidenaut request binding supplies the exact workspace root and operation scope. The verifier does not select a workspace based on executor claims, create worktrees, or accept caller-declared changed paths. Scope checks reuse the run's existing `approved_scope` and role-specific test/implementation path split.
- Repository identity binds the canonical worktree root, worktree-specific Git directory, and common Git directory. Admission and acceptance must resolve to identical values. `HEAD` is recorded as a verified commit ID and must remain unchanged through acceptance.
- Snapshot status uses `git status --porcelain=v2 -z --untracked-files=all` with a command-scoped `core.filemode=true` override so executable-bit changes are detected consistently without changing repository configuration. Capture its exact output bytes. Parse all supported v2 record kinds, including both paths in rename/copy records. Unsupported or malformed records, incomplete/truncated Git output, unreadable paths, identity mismatch, changed `HEAD`, or unstable snapshots raise explicit workflow errors and cannot be converted to an empty delta or successful acceptance.
- Ignored untracked paths are excluded because this status command does not report them. Tracked files remain included when modified, even if they match an ignore rule. An ignored untracked path alone is not an accepted change.
- Snapshot digest is SHA-256 over the exact domain tag `fidenaut-r5-snapshot-v1\0`, followed by unsigned 64-bit big-endian length-prefixed records: exact status bytes, an unsigned 64-bit big-endian entry count, then affected paths sorted by raw filesystem-encoded path bytes. Each path record contains path length and bytes, one object-kind byte (`f` regular, `l` symlink, `x` absent), six ASCII mode bytes (`100644`, `100755`, `120000`, or `000000` for absence), content length, and raw regular-file bytes or raw symlink-target bytes. Deleted paths carry kind `x`, mode `000000`, and zero content length. Length prefixes and kind tags prevent ambiguous concatenations. File content is streamed into the hash; it is not copied into workflow state.
- The G-record's `baseline` has `repo_identity` (`worktree_root`, `git_dir`, `common_git_dir`), `repo_head`, `tree_digest`, and `entries`. Each entry has `path_b64` (canonical RFC 4648 base64 of raw relative path bytes), `kind`, `mode`, `sha256`, and `byte_length`; absent entries use null mode/hash and zero length. Entries are unique and sorted by decoded path bytes. This is verification metadata in the existing G-record, not a second artifact store.
- Each accepted delta entry has `path_b64`, `change`, `before`, and `after`. `change` is one of `added`, `modified`, `deleted`, `mode`, or `symlink`; before/after are null for absence or `{kind, mode, sha256, byte_length}` otherwise. Emit at most one entry per path in decoded-byte order. Classify additions/deletions first, then symlink/type changes, then mode changes, then content modifications; before/after hashes and modes preserve all changed values when multiple attributes change together. Rename is represented as deletion plus addition; a same-path regular-file/symlink type change is a `symlink` change. A delete/recreate that leaves identical final bytes and Git-relevant mode has no net delta. Invalid base64, duplicate paths, traversal paths, and unrepresentable paths fail closed.
- Delta is compared path-by-path with the admission snapshot, using the unchanged `HEAD` tree for paths clean at admission. Fidenaut checks each changed decoded path against `approved_scope` and the existing role-specific test/implementation path split. A `READ_ONLY` reviewer succeeds only with an empty delta.
- Each operation has one required primary output at the Fidenaut-derived G-record `output_path`, canonically stored as `ops/<op_id>/<kind>` relative to `<run_root>`. This path is generated after `op_id` allocation and does not mutate the immutable request or its fingerprint; executor-supplied output paths are not authoritative. No executor artifact manifest or alternate evidence path is authoritative. Successful G-record `result` contains `{executor_result, accepted_artifact, accepted_delta}`; executor claims remain informational, while the accepted fields are Fidenaut-computed. The accepted-artifact shape is `{path, sha256, byte_length}`; `path` is the canonical G-record path, with a Fidenaut-computed lowercase SHA-256 and nonnegative byte length. The parent G-record binds it to `op_id`, role, context/generation, base, and governance revision. Missing/unreadable output, wrong operation-scoped path, role/binding mismatch, symlink escape, or bytes that change during the required re-read are rejected. Completeness means the required output exists and was read stably in full; semantic completeness of arbitrary artifact content is not claimed.
- Executor-supplied output paths, hashes, lengths, and identity claims are not evidence. Acceptance reads only the G-record's Fidenaut-derived operation-scoped path and computes its own hash/length. False executor claims cannot make invalid or missing authoritative bytes pass; claim mismatch alone does not reject independently verified authoritative bytes.
- Snapshotting uses two complete consecutive observations of status and affected-path metadata/content. If the observations differ, fail with an unstable-read error. Admission and acceptance perform these checks while holding the existing governance operation lock; executor completion/context locking ensures the governed turn is no longer writing. The snapshot detects changes during verification but does not claim an atomic filesystem transaction against arbitrary out-of-band writers after the final read.
- Admission preserves the existing lock order: global operation-ID lock, per-run role-work lock, then state-write lock. Acceptance uses the per-run role-work lock and the existing state-write lock/CAS. A verification or persistence failure leaves the operation unaccepted and existing state intact; a retry must reread and reverify, never reuse a cached verification result. Duplicate exact terminal acceptance is read-only replay; stale in-flight state cannot overwrite a newer revision.
- Pre-R5 operation records without baseline/output-path fields remain readable as history. An open pre-R5 operation cannot be accepted as succeeded because its original admission baseline is unavailable.
- No executor/provider/model process is required. No executor claim is authoritative for repository state or evidence bytes.

## Acceptance tests

| Criterion | Deterministic evidence |
|---|---|
| Admission binds repository identity, HEAD, status, dirty bytes, and baseline manifest | Temporary Git worktree tests assert stored identity/HEAD, recompute the framed digest independently, and inspect manifest path/mode/type/hash/length values for tracked edits, untracked files, staged changes, deletions, executable bits, and symlinks. |
| Fidenaut computes final delta without declared changed paths | Mutate the real temporary worktree after admission; assert exact `path_b64`/`change`/before/after schema and ordering for add/modify/delete/mode/symlink. Supply false executor claims: invalid authoritative bytes still fail and correct authoritative bytes verify regardless of claim hash/path. |
| Ignored-path behavior follows the pinned status command | Create ignore rules and ignored untracked files; assert exact status output, no baseline/delta entry for those files, and an empty delta when they are the only changes. Modify a tracked ignored-pattern file and assert its change is included while ignored untracked paths remain excluded. |
| Scope, path, and reviewer restrictions fail closed | Exercise traversal, absolute/out-of-scope, symlink-escape of the operation-scoped output, wrong-operation output location, and wrong-role binding; assert rejection and unchanged persisted state. A `READ_ONLY` reviewer with any delta is rejected. |
| Evidence is re-read and verified by Fidenaut | Use the immutable request's operation-scoped primary output file and assert the exact accepted-artifact schema/hash/length. Delete or truncate the file during verification or mutate it between reads; assert rejection without terminal success. Show that false executor claims cannot validate bad bytes and do not override valid Fidenaut-verified bytes. |
| Identity, HEAD, revision, and snapshot stability fence acceptance | Change worktree identity, HEAD, or governance revision between admission and acceptance; inject differing consecutive snapshots and incomplete Git output; assert explicit rejection, unchanged operation status, and no empty-delta success. |
| Ambiguous file transitions are deterministic | Test delete/recreate with same and changed bytes, rename, and regular-file/symlink type change; assert the specified net delta or explicit rejection. Use a second same-host worktree to prove it cannot affect the operation-bound worktree's result. |
| Persistence and concurrency preserve governance invariants | Race admissions and stale acceptances; inject a failed state write after verification; retry and assert re-verification; assert G9, compare-and-swap behavior, byte-identical prior state after failure, and no acceptance without successful Fidenaut verification. |
| Existing operation history remains readable | Load a pre-R5 terminal record without R5 fields and assert it remains readable; assert a pre-R5 open operation cannot become succeeded without its admission baseline. |
| Scope remains provider-independent | Focused tests run without provider/model/executor processes; inspect that no second artifact store or publication transaction is created. |

For each criterion, implementation evidence records the reviewed revision, exact focused test command(s), temporary-repository setup, expected and observed result, and any mocks or manually constructed state. Tests must exercise Git and filesystem behavior for the changed R5/evidence paths rather than mock it away.

## Failure handling

- Invalid repository/worktree identity, missing `HEAD`, malformed/truncated status, unsupported object kind/status record, unsafe path, unstable read, changed base or governance revision, missing/incomplete output read, or failed re-read produces an explicit `WorkflowError` and does not accept a delta.
- Verification failure cannot be returned as an empty delta, `succeeded` result, or successful artifact record.
- Do not weaken existing role-operation state transitions, G9, lock order, revision checks, or terminal immutability.
